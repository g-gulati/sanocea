# Live Demo #2 — Open-Source / GitHub Landscape Audit

Research only. No code, connector, or domain change was made as a result of this document. Written per
CLAUDE.md's OSS-first rule, applied specifically to the components needed for Live Demo #2 (multi-channel
AI operations + autonomous resolution + WhatsApp/email owner approval).

Evidence hierarchy: official platform docs > official self-hosted project docs > GitHub repo itself
(readme, license file, commit history, issues) > secondary blog/marketing coverage. A GitHub repo's own
marketing claims are never treated as proof an underlying external API exists — verified separately
against official platform documentation per component.

## TOP OPEN-SOURCE COMPONENTS WORTH USING =
n8n's built-in WhatsApp Trigger + WhatsApp Business Cloud nodes (already installed, zero new dependency, matches the already-proven email-ingress pattern) — the single highest-value reuse this pass, since it removes the need to hand-build Meta webhook signature verification and message parsing.

## COMMODITY CODE WE SHOULD STOP BUILDING OURSELVES =
Nothing new this pass beyond what n8n already covers (webhook receipt/parsing plumbing). Meta's WhatsApp send call itself is small enough (~1 endpoint) that "stop building it ourselves" does not apply — there is no meaningful commodity layer left to outsource once the webhook-handling piece is covered by n8n.

## EXISTING SANOCEA COMPONENTS THAT ARE BETTER LEFT ALONE =
Amazon/Flipkart/WooCommerce connectors (already real, already contract-sourced, already carry SANOCEA-native audit/idempotency — no wrapper library improves on this); the 2.5s Command Center polling mechanism (just hardened this session, replacing it now trades a working system for new failure modes); `WorkflowExecution`'s existing pause/resume shape (already sufficient, no gap evidenced).

## COMPONENTS THAT WOULD CREATE UNNECESSARY DEPENDENCY =
Routing WhatsApp approval messages through Chatwoot (adds a second stateful system tracking the same approval event — violates the user's own explicit "Chatwoot must not become the authoritative approval system" rule); any third-party price-monitoring tool for Flow B (wrong shape, no governance/policy concept, would need to be rebuilt around anyway); any WhatsApp Python SDK wrapper for a single-endpoint send call.

## GITHUB FINDINGS THAT CHANGE THE CURRENT IMPLEMENTATION PLAN =
One real, actionable finding: n8n's WhatsApp Trigger node has **documented flakiness in the community** — open n8n GitHub issues (`n8n-io/n8n#19157`, `#19158`, `#14285`) report the WhatsApp Business Cloud credential type missing from the UI and intermediate nodes not firing after the trigger. This means the inbound (reply→SANOCEA) leg should **not** be certified as working purely because it worked once in n8n's UI — it must be tested directly against the installed `n8n@1.98.2`, with a direct Meta-webhook-to-`apps/api/app.py` fallback route designed in from the start rather than added reactively if n8n's node fails during a real prospect meeting. This directly informs increment E/F: build the direct webhook route as the primary path (SANOCEA fully owns verification), and treat n8n's WhatsApp Trigger as an optional alternate wiring, not the sole mechanism the live demo depends on.
