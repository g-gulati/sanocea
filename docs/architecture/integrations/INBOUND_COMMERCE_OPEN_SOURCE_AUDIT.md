# Inbound Commerce Events / Order Operations — Open-Source Landscape Audit

Phase -1 (mandatory pre-work) for the planned inbound-commerce-event capability. Research only — no
code written, no dependency installed. GitHub is treated as discovery, not authority: any claim about a
marketplace/courier API's current availability is checked against that provider's own official
documentation, or marked UNVERIFIED/HISTORICAL where it could not be.

SANOCEA already has real, contract-built connectors (Amazon SP-API, Flipkart Seller API, WooCommerce,
Shopify/Shopify Live, BigCommerce, Meesho) built directly from each platform's own official
documentation — see `docs/connectors/amazon-certification.md`, `docs/connectors/flipkart-certification.md`.
That precedent is the bar every candidate below is measured against, not "does something exist on
GitHub."

## Answers to the required fields

**SERIOUS REPOSITORIES REVIEWED** = ~14 (Medusa, Saleor, ERPNext/Frappe, 4 Shiprocket wrappers, python-amazon-sp-api, 2 Indian-courier-tracker aggregators, CloudEvents spec, n8n's own integration catalog, plus a pass over Vendure/Solidus/Spree/OFBiz/Kill Bill at a shallower depth).

**ADOPT** = None. Nothing found meets the bar of "materially reduces real engineering work without requiring SANOCEA to surrender canonical/authoritative state."

**INTEGRATE** = n8n as the transport/trigger layer for future webhook/polling ingress (Shopify order-created, any REST webhook source) — exactly the same role it already plays for email ingress, never as a data or workflow owner.

**BORROW** = (1) CloudEvents' envelope shape for `ExternalCommerceEvent`, hand-written, no SDK dependency. (2) Shiprocket/Amazon/courier wrapper repos as a *discovery aid* for endpoint lists only, never as installed code — the actual connector gets built from each provider's own official docs, matching the existing Amazon/Flipkart precedent exactly.

**ALREADY COVERED** = Resumable/paused workflow state (`WorkflowExecution`, `Approval`+`ApprovalService` — just extended and hardened for the WhatsApp-approval track), idempotency (`IdempotencyService`, already reused across email ingress, connector mutations, and now notifications), audit (`AuditLedger`), exception queue (`ExceptionRecord`), reconciliation (`ReconciliationResult`), tenant isolation (`TenantAccessError`) — a genuinely complete, real foundation already exists; the gap is not any of these primitives, it's that nothing external currently *feeds* them automatically (see the companion SANOCEA-capability audit for the exact "wired vs. exists" breakdown).

**REJECT** = Every complete OMS/commerce platform (Medusa, Saleor, ERPNext, Vendure, Solidus, Spree, OFBiz) as anything other than a pattern-reading exercise; every third-party Shiprocket/courier wrapper as a dependency; the (non-existent) n8n Shiprocket node claim.

**BEST ORDER-INGESTION COMPONENT** = None found worth adopting — SANOCEA's existing `Order`/`OrderLine` canonical model plus a hand-built `ExternalCommerceEvent` normalization layer (CloudEvents-shaped envelope, SANOCEA-owned payload schema) is the right approach, mirroring how `email_ingress` already normalizes one external input type into the same canonical pipeline.

**BEST MARKETPLACE CONNECTOR APPROACH** = Unchanged: build directly from each platform's official docs, exactly as Amazon/Flipkart/WooCommerce already were. No open-source shortcut clears the bar.

**BEST SHIPROCKET APPROACH** = Build a real connector from `apidocs.shiprocket.in` (official docs + public Postman workspace confirmed available) following the exact same connector_sdk pattern (`MarketplaceConnector`-style auth/transport separation) already used for Amazon/Flipkart. No third-party wrapper is trustworthy enough to depend on for this.

**BEST NDR/RTO COMPONENT/PATTERN** = No open-source component; the *pattern* worth keeping is Shiprocket's own documented state shape (NDR → reattempt-or-RTO decision → RTO-delivered) mapped onto SANOCEA's existing `Shipment`/`TrackingEvent` models plus a new `NDR`-flavored `ExceptionRecord` category, resolved through the same `PolicyEngine`/`Approval` path already built for channel-operation corrections — not a separate mechanism.

**BEST RETURNS/REFUNDS COMPONENT/PATTERN** = Already covered — SANOCEA's own `Return`/`Refund`/`Exchange` models and `post_order/operations.py` service already implement this lifecycle; no open-source pattern reviewed improves on it.

**BEST EVENT-NORMALIZATION APPROACH** = A SANOCEA-owned `ExternalCommerceEvent` Pydantic model shaped like CloudEvents' five-field envelope (`id`/`source`/`type`/`time`/`data`) wrapping a SANOCEA-defined, versioned `data` payload per event type — borrowing the envelope idea, owning the schema, no dependency added.

**BEST RECONCILIATION COMPONENT/PATTERN** = Already covered — `ReconciliationResult` + the `reconcile()` method every connector already implements (see Amazon/Flipkart's own `reconcile()` for order-status divergence detection) is the right shape to extend for settlement/NDR reconciliation too.

**CODE WE WERE ABOUT TO BUILD THAT ALREADY EXISTS** = The resumable-approval/pause-resume mechanism (just built and hardened for channel operations) is directly reusable for order exceptions with zero new approval infrastructure — this is the single most important finding: the notification/WhatsApp work already generalizes.

**CODE SANOCEA STILL MUST BUILD** = (1) `ExternalCommerceEvent` ingress model + normalization layer, (2) a real Shiprocket connector built from official docs, (3) an `ExternalCommerceEventService` that dedupes/routes events into existing canonical models (Order/Shipment/Return/etc.), (4) NDR/RTO-specific policy rules in `PolicyEngine`, (5) Command Center rendering for the order-lifecycle and NDR-lifecycle stories (reusing the same executive-grid + drilldown + WHY-panel pattern already built for Channel Operations).

**NEW INFRASTRUCTURE ACTUALLY REQUIRED** = None beyond what's already in the repo (Postgres, the existing idempotency/audit/policy/approval services, n8n as an optional transport). No new database, queue, or workflow engine is justified by anything found in this research.

**NEW INFRASTRUCTURE NOT JUSTIFIED** = A dedicated workflow engine (Temporal or otherwise) — nothing in this research surfaced a gap the existing `WorkflowExecution`+`Approval` combination can't handle at this scale; a message queue/event bus (Kafka, RabbitMQ, etc.) — inbound event volume for a demo/early-stage merchant doesn't need one, and the existing idempotency-guarded direct-write pattern (proven under real concurrency testing on the channel-operations track) is simpler and already battle-tested; CloudEvents as an installed SDK (the envelope idea is worth borrowing, the dependency is not).
